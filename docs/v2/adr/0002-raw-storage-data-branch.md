# ADR-0002. 원천 데이터는 data 브랜치에 실행 단위 JSONL로 쌓는다

- 상태: 제안 (2026-10-24)
- 결정: orphan `data` 브랜치에 `raw/articles/dt=YYYY-MM-DD/<runId>.jsonl`, `raw/runs/dt=YYYY-MM-DD/<runId>.json`을 추가만(append-only) 한다.

## 배경

v2에는 상시 DB가 없다. 원천은 매 집계 때 처음부터 다시 계산할 수 있어야 하고(재처리 가능성), 어떤 실행이 무엇을 가져왔는지 추적할 수 있어야 한다(대사).

## 검토한 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **data 브랜치 JSONL** | 무료, 변경 이력이 곧 감사 로그, 사람이 읽을 수 있음 | 저장소 크기 증가, 동시 push 충돌 |
| GitHub Releases 첨부 | 저장소 히스토리와 분리 | 파일 단위 관리·조회가 번거로움 |
| S3·R2 객체 저장소 | 표준적인 lake 구조 | 계정·비밀값·비용 관리 |
| DuckDB 파일 하나를 커밋 | 조회 간단 | 바이너리 diff, 실행마다 전체 파일 변경 |

## 결과

- 하루 약 400KB, 1년 약 150MB. 1년 안에는 압축 없이 운영하고, 필요해지면 월 단위 Parquet compaction을 추가한다.
- 실행 단위 파일이라 실패한 실행만 골라 지우거나 다시 넣기 쉽다.
- 동시 push 충돌은 ingest 워크플로의 `concurrency`와 rebase 재시도로 막는다.
- 본문 전체는 저장하지 않는다(제목·150자 요약·URL만).
